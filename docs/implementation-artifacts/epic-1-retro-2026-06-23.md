## Ce qui a bien marché

- **Réutilisation du socle natif** : zéro patch core, 2 tables transverses propres, activation idempotente (entité 1 via `ON DUPLICATE KEY`). Architecture tenue.
- **Régularisation BMAD réussie** : malgré un démarrage hors-cycle, les 3 stories ont été rétro-documentées, validées et reviewées sans rework de fond.
- **Review 3-layer efficace** : a capté de vrais défauts (fallback i18n non traduit, fuite ressource SQL, erreur d'`init()` non propagée) tous corrigés en v0.1.0.
- **Vérification runtime concrète** : la démo a permis de confirmer l'activation réelle sur la cible principale (23.0.3), pas seulement `php -l`.

## Ce qui a coincé (sans blâme)

- **Démarrage hors-cycle** : code écrit avant create-story/validate. Corrigé + mémorisé (`bmad-cycle-strict`). À ne pas reproduire.
- **Faux positif de convention** : la review (Sonnet) a signalé l'absence de la guard `!defined('DOLIBARR_INC_FOR_MODULES')` comme CRITICAL. Vérification empirique : **cette constante n'existe pas dans le core Dolibarr 23 et aucun module P'tite Tête en prod ne l'emploie sur ses pages admin** — l'appliquer aurait cassé les pages. → La convention CLAUDE.dolibarr.md sur ce point est erronée/aspirationnelle.
- **AC partiels** : activation testée sur 23 seulement (pas 19/21). Couverture compat à compléter par la CI.
- **Pas encore de tests** : ni `composer.json` ni PHPUnit → CI tests rendus conditionnels (les tests d'isolation arrivent en E3/E5).

## Leçons clés

1. **Une convention n'est pas une preuve** : vérifier les règles CLAUDE contre le code réel des modules en prod avant de les appliquer/les imposer en review. (cas guard admin)
2. **Le cycle BMAD d'abord** : create → validate → dev → review, toujours ; la régularisation coûte plus cher que de le faire dans l'ordre.
3. **L'isolation se centralise** : tout accès (UI, URL, **API**) doit réutiliser un seul point de validation serveur — ne jamais dupliquer la logique d'isolation (cadré pour E6).

## Découvertes impactant la suite

- **Orphelins `fk_user`** (pas de FK vers `llx_user`) : E2 (service) et E3 (switch) DOIVENT valider que `fk_user` correspond à un user actif et nettoyer/ignorer les orphelins (risque de réattribution de `rowid`).
- **Nouveau scope Epic 6 — API REST** (demande utilisateur) : dépend de E2+E3, réutilise le contrôle d'isolation. Déjà cadré (epics/prd FR12/architecture).
