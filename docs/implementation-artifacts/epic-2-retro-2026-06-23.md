## Ce qui a bien marché

- **Le cycle BMAD tient** : à chaque story, `validate` capte les trous de spec (défaut obligatoire, format pays, garde entité 1…) et `review` capte les vrais bugs (XSS couleur, fuite ressource, redirect cassé). Aucune dette de fond accumulée.
- **Service = point unique** : tenu sur les 4 stories, aucun SQL dispersé dans les pages → E3/E6 auront une seule surface à valider.
- **Isolation vérifiée tôt** : 2-3 est la 1re écriture de données rattachées à une entité ≠ courante (`llx_const entity=N`) — la review a confirmé zéro fuite (`dolibarr_set_const(..., (int)$entity_id)`, jamais `$conf->entity`).
- **Leçon E1 (A1) appliquée** : 3 faux positifs de review rejetés AVEC preuve (colonne `statut` via DDL réel, `FOR UPDATE` inutile, double-escape avant helper core). On ne suit plus une review aveuglément.

## Ce qui a coincé

- **Faux positifs récurrents en review** : la review Sonnet reste prompte à réclamer des choses fausses (double-escape qui corromprait les données, colonne renommée inexistante). Coût : vérification systématique. Mitigé en passant la liste des faux positifs connus au reviewer.
- **Convention CLAUDE erronée non corrigée** (A1 E1 toujours ouverte) : la guard `DOLIBARR_INC_FOR_MODULES` continue d'être un piège ; il a fallu l'exclure explicitement à chaque review.
- **CI jamais exécutée** (A3 E1) : tout le code E1+E2 n'a encore tourné sur aucun runner GitHub.

## Découverte impactant E3 (CŒUR sécurité)

- **`getUserEntities` filtre l'utilisateur actif mais PAS l'entité active** : un user peut conserver une affectation vers une entité ensuite désactivée. **E3 (switch) DOIT décider** : une entité autorisée mais désactivée est-elle « switchable » ? Recommandation : **non** — le switch valide `entity_id ∈ autorisées(user) ET entité active`. À cadrer en story 3.3 (contrôle d'accès serveur). (Issue F-12 de 2-1.)
